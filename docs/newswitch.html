01

The big picture

newswitch is a FastAPI app whose entire functional surface is managed by an arkitekt agent embedded in the server. Nothing in the backend defines REST endpoints for microscope features by hand. Instead, everything is registered on an app registry that create_registry creates fresh for every app. Modules only declare plain functions and plain @dataclass models and states (no decorators); create_registry imports them by name and registers them explicitly, according to the device configuration:

  • functions registered with app.register_action (in create_registry) become remotely callable actions;
  • data classes registered with app.register_state become reactive shared state, pushed to every browser as JSON-patches;
  • service classes registered with app.register_context (the “managers”) are dependency-injected into those functions by type annotation;
  • the frontend generates typed React hooks from the backend’s schemas (a committed export of a complete microscope, frontend/schemas/), so UI code never hand-writes API calls.

02

arkitekt concepts, one by one

An app registry per app

create_registry(devices, services=()) in newswitch/microscope/registry.py creates a fresh App("newswitch", app_context=Settings) and explicitly registers, by name, what the device configuration has: the models, the core, one group per configured part and the actions needing several parts; the entry file then adds how the frames are watched and the configuration’s UI. Nothing registers itself on import and no module holds an app: two apps in one process share nothing. The stack is four packages, pinned exactly in backend/pyproject.toml:

  • arkitekt 8.0.0 — the App facade, Task, OptimisticInput, bsx, withValidator;
  • arkitekt-runtime 5.0.0 — the agent, actors, locks, evented states, the journal;
  • arkitekt-spec 3.18.0 — the declarations (implementations, schemas, ports);
  • arkitekt-fastapi 2.1.0 — the served agent: configure_fastapi, /schemas/*, journal routes, AsyncAgentTestClient.

Agent and actors

arkitekt uses the classic actor model. Translated to newswitch:

The Agent (FastApiAgent, created by configure_fastapi in create_app) is the runtime container for the whole app. It does not do microscope work itself. It owns:

  • contexts — the live manager instances (everything app.register_context), keyed by name (newswitch’s own routes do not look them up here: they read them off the registry’s Microscope, see §06);
  • states — the live state instances (everything app.register_state), each with a revision counter and a serialized (“shrunk”) copy;
  • locks — named task locks such as stage_position;
  • the implementation map — one entry per declared action;
  • the startup and shutdown hooks and the background workers;
  • all running assignments (tasks) and the actors executing them;
  • the journal, persisted in SQLite (arkitekt_agent.db, db_path in base_config.yaml) — what reconnects resume from and the frontend /replay page reads. The old agent_data.db of the rekuest-next days cannot be read by the new store.

An actor is the execution vehicle for one implementation. When a client assigns a task (“run move_stage with these args”), the agent routes the assignment to that implementation’s actor, which runs the function — sync functions in a worker thread via koil, async ones on the loop — and reports lifecycle events back: STARTED, PROGRESS, YIELD, PAUSED, HELD, CANCELLED, COMPLETED, FAILED.

Why it looks different from Arkitekt

In upstream Arkitekt the agent connects out to an arkitekt server and receives assignments from there. In newswitch arkitekt-fastapi replaces that transport: the agent lives inside uvicorn and browsers talk to it directly over /ws plus a few REST routes. Same model, no external server. Served by main_arkitekt.py (python main_arkitekt.py) newswitch does connect out, as a plain arkitekt agent — see Two ways to serve.

The app context

App("newswitch", app_context=Settings) declares which class is the app context — the one settings object of a deployment. Settings lives in newswitch/settings.py and reads base_config.yaml. There is no marker decorator; the declaration on the App is all there is.

The object you pass as app_context= into configure_fastapi travels into agent.aprovide(context=…) and becomes injectable by type into hooks and actions. That is why the startup hooks (provide_stage(app_context: Settings), …) receive the config: the parameter’s type annotation is matched against the app-context class. The served app refuses to start without one (require_app_context in the lifespan).

app.register_startup — the composition root

# newswitch/microscope/parts.py: data and functions
parts = configured_parts(devices)          # Parts(stage=True, detector=True, …), a value
build_microscope(settings, devices)        # -> Microscope: a record of every state and manager

# newswitch/microscope/registry.py, in create_registry:
built: list[Microscope] = []

def microscope(settings: Settings) -> Microscope:    # one build, on the first hook
    if not built:
        built.append(build_microscope(settings, devices))
    return built[0]

if parts.stage:
    async def provide_stage(app_context: Settings) -> Tuple[StageManager, StageState]:
        m = microscope(app_context)
        return m.stage, m.stage_state

    app.register_startup(provide_stage)
…

Startup hooks run once, when the agent boots (inside aprovide, before anything is callable). Two pieces of magic, both driven purely by type annotations:

  1. Parameter inspection — the “app-context, state, and context dependencies”: each parameter is matched by its annotated type against (a) the app-context class, (b) already-published state classes, (c) already-published context classes. Matching objects are injected.
  2. Return annotation → publication — the Tuple[…] return annotation tells the agent what each returned object is. Objects whose class or protocol is a context go into agent.contexts; objects whose class is a state go into agent.states (serialized, revision 0, immediately subscribable).

So create_registry is the composition root: it defines one startup hook per part (provide_core, provide_stage, provide_illumination, provide_detector, provide_objective, provide_filter_bank, provide_uc2, and provide_focus for the focus group, stage + detector), closures with static Tuple[…] return annotations, next to the registration of what they provide, only for the configured parts. Startup hooks get only the app context injected (no states or contexts exist yet) and none sees what another returned, while the parts depend on each other (the simulated detector reads four other states, acquisition and hooks use several managers, the UC2 parts share one bus); so all hooks hand out the objects of one build_microscope, made on the first hook and kept in create_registry’s closure. A part the configuration lacks is never constructed (on hardware nothing talks to the bus for it); the states shared managers read of it (light path, metadata, the simulated detector) stay empty. Everything a hook returns is published for the rest of the agent lifecycle and becomes injectable into every action, background worker and shutdown hook. app.register_shutdown hooks (save_device_config, if the microscope was started; close_detector) run on teardown, after background workers and running tasks are cancelled.

Footgun

If you build a new manager and forget to add it to both the returned value and the return annotation, injection fails at call time with StateRequirementsNotMet.

Context dependency means “give me the live manager instance of this type” (e.g. stage: StageManager). State dependency means “give me the live shared state instance” (e.g. state: StageState). Contexts are never serialized; states are.

app.register_action — actions

Any function becomes a remotely callable action:

# newswitch/actions/stage.py: a plain function
def move_stage(stage: StageManager, task: Task, x: float | None = None, …) -> None:
    stage.move(x=x, …, task=task)

# newswitch/microscope/registry.py, in create_registry, when a stage is configured
app.register_action(stage.move_stage, optimistics=[OptimisticInput(state="StageState", path="/x", accessor="/x"), …])
  • Parameters that are contexts or states are injected and stay invisible to callers; everything else becomes the action’s argument schema (its “ports”), which is what the frontend codegen turns into a zod schema.
  • Progress and pause: there is no ambient progress(). An action takes an injected task: Task and calls task.progress(pct, msg) and task.pausepoint(), passing the task down explicitly (StageManager.move(…, task: Optional[Task] = None)). Tests calling an action directly pass Task.local().
  • locks=[…] declares the action’s locks explicitly; otherwise they are inferred from the contexts and states it takes (see §05).
  • optimistics=[…] describes how the UI should predict the state change before the backend confirms it — instant slider and position feedback. path and accessor are JSON pointers.
  • Argument validators are blok UtilCalls built with withValidator("len(value) > 0", error_message=…), evaluated in the frontend by src/lib/arkitekt/calls.ts.
  • Nothing is registered at import time: a function becomes an action when create_registry calls app.register_action(fn, …) on the registry it creates.

app.register_background — daemons

app.register_background functions are long-running workers started right after the startup hooks; async ones run on the event loop, sync ones in a dedicated thread. They use the same injection: run_uc2_bus(uc2_bus: UC2BusManager) gets the live bus. newswitch runs three — the detector acquisition loop, the UC2 bus connection pump, and the UC2 event → state dispatcher.

Registering classes

Models and states are plain @dataclasses; registering them does not change the class, so any number of registries can take the same one.

RegistrationFromWhat it does
app.register_context arkitekt.App Marks a class (usually a Protocol) as an injectable service — a “manager”. locks=[…] are the locks every action taking this context holds.
app.register_state arkitekt.App The heavy one. Introspects the class into a state schema (a port per field) and makes instances evented: every setattr applies the change under the state’s own RLock and publishes a JSON-patch with a new revision to all subscribers. required_locks=[…] are the locks every action taking this state holds; writes are not checked against locks.
app.register_model arkitekt.App Marks a dataclass as a serializable data structure so it can appear inside action arguments, returns and state fields. Its identifier is @newswitch/<snake_name>; enums travel by member name ("SEQUENTIAL"). Used for config and value objects (StageConfig, Illumination, UC2CanBusConfig). No reactivity.
@runtime_checkable stdlib typing Not arkitekt at all. Allows structural isinstance(obj, SomeProtocol) checks, which the tests use (isinstance(bus, UC2BusManager)).

The app registry and bloks

app.registry is an app’s AppRegistry — the accumulator for everything above: implementations, state schemas, locks, bloks, hooks. create_registry creates one and registers everything on it explicitly, by name, based on the device configuration, and create_app serves it:

  1. the models, always (register_models(app));
  2. the core every microscope has: io, hooks, expanse, calibration, light path, metadata, cache, the action clear_expanse;
  3. one group per configured part — stage, illumination, detector, objective, filter bank, UC2 board (a uc2-rest or canopen controller) — each with its states, contexts, startup hook, actions (newswitch/actions/<part>.py) and background tasks;
  4. what needs several parts, when all are there: the focus group (stage + detector, parts.focus: the state AutofocusState from provide_focus, and run_autofocus, calibrate_light_path, scan_region); acquire_multidimensional_acquisition (stage + detector + illumination); run_uc2_event_dispatch (UC2 board + stage).

The detectors send their frames to the context FrameSink (a runtime-checkable protocol, newswitch.broadcasters.FrameSink), which the core registers but does not provide: the entry file provides it with a startup hook of its own, and passes in the arkitekt services the App is created with. The background run_detector_loop(detector: DetectorManager, sink: FrameSink) gets both contexts injected and calls detector.acquire_live(sink). The entry file also registers how the frames are watched and the configuration’s UI on the returned app (Two ways to serve).

def create_registry(devices: NewswitchConfig | None,
                    services: Sequence[Service[Any]] = ()) -> App:
    app = App("newswitch", app_context=Settings, services=services, root=ASSET_ROOT)
    parts = configured_parts(devices)
    built: list[Microscope] = []
    def microscope(settings: Settings) -> Microscope: …  # build_microscope(settings, devices), once
    register_models(app)
    app.register_state(IOState, required_locks=[locks.IO])  # … the core
    app.register_context(FrameSink)                        # provided by the entry file
    app.register_startup(provide_core)                     # closures over microscope()
    app.register_action(core.clear_expanse)
    if parts.stage:
        app.register_state(StageState, required_locks=[locks.STAGE])
        app.register_context(StageManager, locks=[locks.STAGE])
        app.register_startup(provide_stage)
        app.register_action(stage.move_stage, optimistics=[…])
    …                                                      # illumination, detector, …
    if parts.focus:                                        # stage + detector
        app.register_state(AutofocusState)
        app.register_startup(provide_focus)
        app.register_action(scan_region)                   # run_autofocus, calibrate_light_path
    return app

# main_fastapi.py: the transport and the UI, on top
async def provide_frame_broadcaster(app_context: Settings) -> Tuple[FrameSink]:
    return (FrameBroadcaster(),)             # the detectors’ sink: the live view’s broadcaster

def create_fastapi_registry(devices: NewswitchConfig | None) -> App:
    app = create_registry(devices)
    app.register_startup(provide_frame_broadcaster)
    declare_ui(app, devices)                 # the config’s ui
    return app

Without a configuration only the models and the core are registered: clear_expanse is the only action. The configuration’s bloks are validated strictly against what was registered: a blok calling an action whose device is absent is refused.

You can register any function whose non-injected parameters are serializable types — that is how a new “app” (in the ImSwitch sense) gets its backend surface. When the server starts, the agent serves a validated, frozen snapshot of the registry.

A blok is different: it ships a server-defined UI fragment written in a JSX-like markup. Bloks are served at /schemas/bloks and read by the frontend at run time, nothing about the UI is built in, then rendered by the frontend’s blok renderer. They are not written in Python: they are the ui section of the device configuration, checked against the catalog the frontend publishes (newswitch/bloks/newswitch-catalog.json, versioned as newswitch@<n>). Written in blok language v2, bloks can bind to states ({self.ObjectiveState.mounted_lenses}), loop (<foreach>) and invoke actions (onClick={self.switch_objective(slot: lens.slot)}). Use them for small panels that should not require a frontend build.

04

Request lifecycle — what a button press does

  1. A component calls a generated hook: useMoveStage().call({x: 100}).
  2. The transport POSTs to /assign with the implementation name and args; the args were validated client-side against the generated zod schema (and any withValidator calls).
  3. The agent records the assignment and hands it to the actor. If another running action holds one of its locks, it waits until that lock is released; then the function body runs with its contexts, states and task injected.
  4. Lifecycle events and LOCK/UNLOCK frames stream to every subscribed client over /ws; the UI’s ProgressDisplay and lock indicators react. Other clients see the task too (ASSIGN).
  5. Any state mutation — inside the call, or from elsewhere such as the UC2 dispatcher writing StageState.x — is JSON-patched over the same socket.
  6. Cancel, pause and step buttons hit /cancel, /pause, /step. task.pausepoint() in the body is where pauses take effect; cancellation raises CancelledError inside the body, which the UC2 bus turns into a hardware stop command.
  7. Every event lands in the journal, persisted to SQLite, feeding /replay.
05

State, locks and the journal

  • A state instance is a normal Python object — mutating an attribute is the entire API (stage_state.x = 42.0). The evented subclass publishes {op: replace, path: /x, value: 42.0, rev: n} to the agent, which fans it out to /ws subscribers; each frontend zustand store applies patches in revision order. Thread safety of the write is the state’s own RLock.
  • Locks are action locks, nothing else. An action’s locks are its explicit locks= or are inferred from the contexts and states it takes (a state’s required_locks, a context’s locks). They do two things: an action waits until no other running action holds the same lock — real mutual exclusion, command exclusivity over a device for a whole multi-step operation — and the UI is told (LOCK/UNLOCK) so it can disable conflicting actions. The names are the constants of newswitch/microscope/locks.py, one per part (and shared service): STAGE ("stage_position"), ILLUMINATION, DETECTOR ("camera_parameters"), OBJECTIVE, FILTER_BANK, GALVO, IO, HOOKS ("hook_registry"), EXPANSE ("expanse_state"), CACHE; each part’s state and manager carry its lock (the ObjectiveManager holds OBJECTIVE), the AcquisitionManager holds EXPANSE and IO, and the UC2 actions name theirs explicitly.
  • State writes are not checked against locks. Managers, background loops (the UC2 event dispatch) and shutdown hooks write states freely. Writes made inside an action through the injected state are attributed to the task (the patch carries its task_id) and refused after the task ended; writes made by managers or hooks directly carry no task id.
  • optimistics=[OptimisticInput(state=…, path="/x", accessor="/x")] on app.register_action lets the UI apply a predicted patch immediately when the call is made; the real patch reconciles it.
  • The journal is one ordered record per agent session: every entry has a pos (1, 2, 3 … no gaps), a global_rev, a kind, a task_id …; the world at any position is states + tasks + locks. It is served at /journal, /journal/{session}, /journal/{session}/at/{pos}, /journal/{session}/at?timestamp=… and /tasks/{id}/events. The older /states/checkout, /states/segments and session boundary routes still exist, but the frontend no longer uses them.
06

Video streaming (separate from /ws)

Bulk pixels never travel through the state system. The detector background loop (run_detector_loop, detector.acquire_live(sink)) pushes frames into the FrameBroadcaster — the FrameSink main_fastapi.py provides — which keeps the newest frame per slot. Browsers open WS /stream/frames/{slot} — the first message is the client’s auth frame — and get whole frames, one per message: the detector’s own values, binned to max_size (default 640; 0 sends full size). The client acknowledges each frame and is sent the newest after that, so a slow viewer skips frames. Scan and acquisition code can broadcast into additional slots, for example stitched-map tiles.

create_app includes the module-level routers of newswitch/routes/ — liveview.router at /stream, files.router (/files/…), cache.router (/cache/…). All read what they need off the running agent’s contexts (running_context(connection, cls) in routes/__init__.py, for requests and websockets): files the IOManager, cache the CacheManager, the live view the FrameBroadcaster (provided as the FrameSink). Before startup the HTTP routes answer 503 and the live-view websocket closes with 1013.

Two ways to serve

The detectors only know the FrameSink protocol (start_broadcasting(), broadcast_sync(slot, frame) from the detector’s thread), a context create_registry registers and the entry file provides. Which sink they get, and which UI is declared, is up to the entry file. Both start the same way (backend/main.py: settings, then load_devices(config, "ui" | "agent_ui"), which raises ConfigError when the device configuration lacks that UI section), call create_registry(devices, services=()), then register on the returned app what is particular to them, among it a module-level startup hook that provides the FrameSink; python main.py fastapi|arkitekt picks one.

main_arkitekt.py runs the registry with arkitekt.run, which logs in to the arkitekt server fakts finds (--url / $FAKTS_URL); it needs the extra agent (arkitekt[rekuest,lovekit], uv sync --extra agent), and only it imports lovekit (newswitch.broadcasters does not import lovekit.py). The startup hook provide_lovekit_sink provides a LovekitSink(cameras_of(load_devices(app_context))) as the FrameSink, and a CameraStreams. The LovekitSink keeps the newest frame per detector; the background hook publish_camera_streams(lovekit, sink: FrameSink, live: CameraStreams) (a sink that is not a LovekitSink is refused with a TypeError) sends what is new, at most MAX_FPS (15) per stream, converting with to_rgba off the event loop (~37 ms per 1920×1200 frame). The declared streams are held in the state CameraStreams, which the agent_ui bloks show (<StructureDisplay value="@stream" />). The agent_ui is checked strictly, offline, against the catalog arkitekt ships (orkestrator@v4.2.1) and the registry; a configuration without one does not start as an agent. The agent serves no HTTP routes: the files the IO manager writes and the frame cache are not reachable from Orkestrator, so a frame’s cache id or a file handle points nowhere there — a known gap. So far the agent is tested offline only, with a fake lovekit client.

The UC2 hardware layer

protocols/uc2.py defines the transport-agnostic UC2BusManager: stage verbs in micrometers, laser and LED in raw PWM, galvo in DAC counts, objective slots and node scan — plus subscribe() yielding typed events (models/uc2.py: PositionUpdate, MotionDone, HomingChanged, EStopChanged, ButtonPressed, NodeSeen, BusError).

Three interchangeable implementations, selected in build_uc2_bus from uc2_transport: UC2CanBus (CANopen via uc2canopen.aio — node map, µm↔steps scaling, event-driven motion-done from TPDO frames), UC2RestBus (serial JSON via uc2rest.aio — single ESP32 master, pattern-keyed firmware events) and VirtualUC2Bus (simulator). Both real buses reconnect with exponential backoff and surface failures as BusError plus UC2State.last_error.

Two background workers keep it alive: run_uc2_bus owns the connection and event pump; run_uc2_event_dispatch consumes subscribe() and mirrors telemetry into StageState and UC2State — the “spontaneous events” path. It writes freely, without a lock and without a task id, so the reported position streams in while a move holds stage_position. Device managers such as UC2StageManager only ever call bus verbs, never a concrete transport.

09

What is the Expanse?

The Expanse is newswitch’s infinite sample-space canvas — the world map of everything that has been imaged. ExpanseState holds placed Images, each with its stage-space affine transform; position, pixel size and orientation come from the MetadataManager and the Kube optics model — the 4×4 pixel→stage affine calibrate_light_path measured for the frame’s light path, or without one the nominal pixel size (the detector’s pixel_size_um / the objective’s magnification). ExpanseManager adds and clears entries; acquisitions push their frames into it. The frontend renders it as the three.js scene in frontend/src/components/stage/ — planes textured from zarr tiles, with camera navigation. clear_expanse is the registered action that empties it.

Conceptually it replaces ImSwitch’s StageMap: a persistent, transform-correct mosaic of acquired fields of view.

Known wart

The module docstring in protocols/expanse.py still reads “Stage Manager Protocol” — a copy-paste leftover, worth fixing.

Frontend in one paragraph

What a backend registers depends on its device configuration (create_registry), but the frontend’s hooks must cover everything newswitch can do. So just export-schemas (uv run python -m newswitch.tools.export_schemas) builds create_registry in-process on the reference microscope backend/newswitch/reference/complete-microscope.yaml (REFERENCE_CONFIG: every part, devices only, no ui; it refuses a configuration missing any part), takes a snapshot of the registry — nothing is started, no app, no startup hooks — and writes exactly what a FastAPI backend on it serves at /schemas/implementations|states|locks into the committed frontend/schemas/{implementations,states,locks}.json — the mirror of the blok catalog, which the frontend exports for the backend. frontend/plugins/generate-app.ts — a Vite plugin run on every dev and build — reads only those files (no backend needed; a missing file fails the build and points at just export-schemas) and emits src/apps/default/hooks/{actions,states,locks}/*.ts — zod schemas plus typed hooks such as useMoveStage and useStageState. Bloks are read at run time instead. The export and these files are committed, and just drift-check (the codegen-drift CI job) re-exports, rebuilds and fails if frontend/schemas, frontend/src/apps diverge from what is committed. The hand-written runtime in src/lib/arkitekt/ (formerly src/lib/rekuest) manages the /ws connection, task assignment, patch application and locks. Its INIT opts into the journal: frames carry pos and journal_session, and on reconnect the client sends resume_after/session_id and receives exactly the frames it missed (a resumed INIT keeps local state; resync: true means start over). It also handles ASSIGN (tasks started by other clients), HELD (status “held”) and SESSION_INIT/STATE_SNAPSHOT (state baselines). The /replay page’s timeline spans the current journal session and shows states and locks at the selected time via /journal/current/at?timestamp= (checkoutAt in the state context). Bloks are rendered by the frontend’s blok renderer. Components in src/components/microscope/ consume only the generated hooks.

Workflow

If you add or rename a backend action, state or lock: run just export-schemas, then cd frontend && yarn build (or just just drift-check), and commit the regenerated files.
